# TL01-P3 — Portable Diagnostic Report

## Purpose

Make the TL01 Doctor actionable, reproducible and reviewable without confusing static findings with exported-runtime proof. This is the final Portability Doctor implementation slice after [P0](tl01-p0.md), [P1](tl01-p1.md) and [P2](tl01-p2.md).

## Commands

Use the existing CLI for a quick review:

    node bin/talarion.mjs doctor
    node bin/talarion.mjs doctor --json

Export a standalone report:

    node bin/talarion.mjs doctor report artifacts/doctor --json

This writes the two deterministic artifacts below:

- artifacts/doctor/doctor-report.json — machine-readable report
- artifacts/doctor/doctor-report.html — responsive local HTML report with remediation guidance

The report command exits nonzero if any error-level Doctor issue is found, **after exporting the evidence**. The destination must be inside the repository and cannot traverse symlinks. Existing \`doctor --json\` remains \`talarion.doctor/v1\` and adds a \`report\` field.

## Stable contract

The standalone report uses \`talarion.doctor-report/v1\`. Every finding has:

- \`findingId\` — \`PFnnn-\` plus a deterministic SHA-256-derived identifier from the rule, relative file path, line, column, affected targets, profile and diagnostic context (including status).
- \`ruleId\`, \`severity\`, \`category\`, \`capability\`, \`targets\`, \`message\` and \`remediation\`.
- Optional source path, line, column, profile/status, required capability, declared path, observed dimensions and limit.

A finding ID stays stable across prose changes or repeat executions with the same source locations and context. It **changes when the identity-bearing source location/context changes**; this is not a permanent semantic code identity across arbitrary refactors.

Deterministic finding order: severity (error before warning before info), relative path, line, column, rule ID and identity context. Exact duplicate occurrences gain a deterministic ordinal, avoiding collisions. Summary counts by severity, rule and target are derived from actionable findings.

## Assessment semantics

- \`fail\`: one or more error diagnostics. The CLI exits nonzero.
- \`review\`: no errors, but at least one warning or info finding. The CLI exits successfully with outstanding review signals.
- \`no-findings\`: no actionable diagnostics. This does **not** certify portability or release readiness.

The report scope always states \`sourceAnalysisOnly: true\`, \`exportedRuntimeEvidence: false\`, \`hardwareCertified: false\`, \`performanceCertified: false\`. Texture dimensions and static profile statuses from P2 remain source-only observations. Device FPS, GPU memory, draw calls and thermals cannot be inferred from a clean Doctor report.

## Human-readable output

The text CLI shows counts, the exact file/line/column, affected target, rule ID and a remediation. HTML presents the same findings, a target profile table and a clear evidence-authority notice. The HTML renderer escapes untrusted filenames, messages, remediations and profile values and requires no browser network dependencies.

## CI and closure

The Node 20/22/24 verification jobs execute the standalone export command. Node 24 also uploads the Doctor JSON/HTML as \`talarion-doctor-report\`. Tests cover stable identifiers, deterministic ordering/bytes, warnings vs errors, source UNKNOWN, output path restrictions, XSS-resistant HTML and CLI exit status. Release acceptance remains tied to independent exported Web/Android runtime state/visual/telemetry gates, not Doctor alone.

Closure requires exact PR-head Node matrix and exported Web/Android TL00 CI PASS without threshold relaxation. Screenshot capture timing hardening remains separate [QA issue #4](https://github.com/ictseoyoungmin/talarion/issues/4).
