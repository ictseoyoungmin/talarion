# TL02-P1 — Metric Units and Budget Coverage

TL02-P1 extends [P0's verified evidence authority](tl02-p0.md) without treating a CI emulator as real-device hardware. It checks **whether an apples-to-apples metric comparison could later be performed**, not whether a performance target has been met.

## Profile vocabulary

Profiles in \`talarion.config.json\` use **schema-fixed units**. Values are positive finite numbers; integer metrics must also be safe integers.

| Config field | Unit | Observed metric | Direction | Required? |
| --- | --- | --- | --- | --- |
| \`targetFps\` | \`fps\` | engine-reported \`fpsP10\` | minimum | yes |
| \`processMsP95Budget\` | \`ms\` | engine-reported \`processMsP95\` | maximum | no |
| \`peakMemoryBytesBudget\` | \`bytes\` | engine-reported \`peakMemoryBytes\` | maximum | no |
| \`drawCallBudget\` | \`calls\` | **not observed** | maximum | no |

The target FPS declaration and renderer draw-call budget already exist in the project. The process P95 and memory peak budgets are optional new values; they are not enabled or graded automatically.

Optional \`performanceUnits\` explicitly checks schema-fixed units. For example:

\`\`\`json
{
  "targetFps": 30,
  "processMsP95Budget": 14,
  "peakMemoryBytesBudget": 67108864,
  "drawCallBudget": 400,
  "performanceUnits": {
    "targetFps": "fps",
    "processMsP95Budget": "ms",
    "peakMemoryBytesBudget": "bytes",
    "drawCallBudget": "calls"
  }
}
\`\`\`

Without \`performanceUnits\`, legacy scalar configuration uses \`unitSource: "schema-fixed"\`. An explicitly matching unit uses \`unitSource: "explicit-validated"\`. Mismatched, unsupported or orphaned unit declarations are **errors**, not silent reinterpretations. An omitted optional budget is \`not-declared\`, not PASS. An absent or malformed profile, a nonpositive target FPS or a fractional draw-call budget is invalid.

## Output contract

The CLI from P0 remains:

\`\`\`bash
node bin/talarion.mjs budget authority \
  artifacts/run/web artifacts/run/android artifacts/parity/performance-authority.json --json
\`\`\`

Each target adds \`budgetCoverage\` with schema \`talarion.budget-coverage/v1\`. The four fixed metrics include a declared limit (or null), observed value (only if trusted and available), unit, comparison direction, \`status\`, \`comparisonEvaluated: false\` and \`decision: "not-evaluated"\`.

Possible statuses:

- \`comparable-not-graded\`: a validated measurement exists and the configured limit uses the correct unit. No budget decision has been made.
- \`unobserved\`: a limit exists but the protocol has no corresponding trusted measurement, such as draw calls.
- \`not-declared\`: optional limit absent; no comparison attempted.
- \`unverified\`: evidence provenance or raw observation validation failed.
- \`invalid-profile\`: profile shape, metric value or explicit unit invalid, and the authority command fails closed.

The output also identifies \`gpuTextureMemoryBytes\` and \`thermalHeadroom\` as unavailable in the current runner protocol. These are not inferred from \`textureMax\` or engine process/memory samples. A profile check has no authority to certify rendering FPS, thermal performance, physical devices or emulator-to-device portability.

## QA and closure

Checks \`PA01\`–\`PA06\` remain unchanged; \`PA07\` validates profile existence/positive supported quantities and \`PA08\` validates explicit units. Both can reject the authority result. CI checks that real exported Web/Android outputs keep all metric decisions \`not-evaluated\`; fixture tests also cover invalid units/types, orphaned unit maps, missing profiles, false metrics embedded in raw samples, stale runner summaries and unreviewed physical Android.

P2 will define reproducible measurement windows and statistically credible regression policy. P3 will produce a reviewable budget-decision report. Neither follows automatically from a successful P1 evidence coverage result. The independent [physical-device certification](release-certification.md) and [visual capture issue #4](https://github.com/ictseoyoungmin/talarion/issues/4) remain open boundaries.
