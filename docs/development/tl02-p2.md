# TL02-P2 — Canonical Measurement Windows and Observational Regressions

This slice makes engine-observed performance telemetry comparable **only after** P0 runner/replay/raw-sample provenance and P1 fixed-unit profile checks succeed. It does not certify target FPS, physical Android performance or GPU resources.

## Canonical window

\`talarion.config.json\` explicitly configures:

\`\`\`json
"performanceWindow": {
  "warmupTicks": 120,
  "sampleStepTicks": 60,
  "minSamples": 5
}
\`\`\`

The actual replay (schema \`talarion.replay/v1\`) supplies the terminal tick and tick rate; for the canonical sample these are tick **600** and **60 Hz**. Source samples are sampled every 60 **replay ticks**, not every second of wall time. Ticks 60 and 120 are warmup and not included. The expected observation set is ticks **180, 240, 300, 360, 420, 480, 540, 600**. This excludes startup but retains all canonical in-game event phases; it does not exclude known action events or inconvenient measurements.

The inspector refuses to claim a complete window when required ticks are missing, duplicated, out-of-order, out-of-range, unaligned, or the profile/replay metadata is invalid, even when some FPS values look acceptable. Recomputed P10 FPS, median FPS, P95 engine-reported processing/physics time, and peak engine-reported static memory are published only for a **complete, verified** window. MAD (median absolute deviation) is reported as a descriptive per-window variation measure. Engine-observed processing time is *not* total render frame time; FPS is not a device benchmark. \`talarion.performance-window/v1\` is nested under each target's existing \`performance-authority/v1\` output.

Possible statuses: \`complete-window\`, \`incomplete-window\`, \`unverified\`, \`invalid-window\`, \`not-configured\`. Invalid window evidence cannot produce metrics. A source-hash-only P0 replay remains usable for P0 tests; without machine-readable replay timings it cannot claim P2 completeness.

## Conservative multi-run regression helper

\`assessObservationalRegression\` emits \`talarion.performance-regression/v1\`. It requires at least **three independent runs per cohort**, a distinct run ID per record, complete verified P2 windows and an identical target, runtime class, explicitly supplied environment key, profile, replay SHA-256, replay tick rate, terminal tick, warmup and sample step/count. It deliberately **does not compare** Android against Web, or mix unlike hosts/devices.

Two user-declared thresholds must be supplied: allowable percent loss of across-run median FPS and allowable percent rise in across-run processing P95. Median absolute deviation across independent runs establishes a deterministic noise fence \`2 × (MAD_baseline + MAD_candidate)\`. The observational statuses are \`regression-observed\`, \`no-regression-observed\`, \`inconclusive-noise\`, and \`not-evaluated\` (incompatible or insufficient evidence). The noise fence is a transparent engineering *heuristic*, **not** a confidence interval or statistical significance test. Repeated runs must genuinely come from separately observed executions; \`runId\` and \`environmentKey\` supplied by callers are metadata, not remote attestation.

The current CI executes **one exported Web run and one Android emulator run**, so it validates the window and intentionally **does not invent a multi-run regression decision**. P3 will establish reviewable multi-run comparisons and budget-report policy. A result of \`no-regression-observed\` is not a pass against declared FPS limits; \`budgetDecision\` remains \`not-evaluated\`.

## Evidence authority and gates

The Node tests exercise fixed exact-tick selection, missing/out-of-range/duplicate/nonfinite samples, malformed windows, P0 invalid-provenance quarantine, dissimilar environment/replay, duplicate run IDs, meaningful regressions, noisy inconclusive results and permutation invariance. Actual Web/Android CI requires complete configured P2 windows alongside existing TL00 state/visual/telemetry QA. No visual thresholds are relaxed.

The independent [QA issue #4](https://github.com/ictseoyoungmin/talarion/issues/4) and separate physical-device [Release Certification](release-certification.md) remain open; an emulator observation never becomes device performance certification.
