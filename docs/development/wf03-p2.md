# WF03-P2 — Google Play Release Readiness (Planned)

Status: **NEXT / NOT IMPLEMENTED**. The verified reference baseline is WF03-P0 signed AAB and WF03-P1 actual AAB-derived Release APK emulator runtime, both confined to the original Signal Garden Three.js WebView host. A disposable CI key and an installable emulator APK **do not** authorize production upload, listing, device support, or Play approval.

## Goal and separation of authorities

Keep five independent verdicts: (1) source/host provenance, (2) signed release AAB build, (3) actual extracted APK gameplay runtime parity, (4) Google Play submission readiness, and (5) **Play Console-confirmed upload/review/publication**. The first three have a constrained automated reference proof; the last two do not.

## P2 implementation boundaries

1. **Application identity:** Stable production application ID/package ownership, branding and versionCode monotonicity against previous Play releases. The fixture `dev.talarion.signalgarden` and CI `versionCode=2` are a demonstration, not proof of an owned existing Play listing.
2. **Signing and custody:** User-provisioned private production upload keystore (outside git and build logs), signed AAB, independent signer fingerprint, Play App Signing enrollment/upload-key lineage and key-rotation policy. CI's disposable signing key must never be treated as production upload authority.
3. **Current submission policies:** Capture official Play policy snapshot with source URL, effective date, review date and scope for target SDK, distribution region, API/ABI applicability, user-data safety/privacy declarations, permissions, ads, content rating, target audience, and Google Play's account-specific testing/verification requirements. **Static lint is not Play acceptance.** Re-check at release time.
4. **Release package gate:** Validate final AAB with pinned bundletool; independently inspect manifest, package/version, Android 64-bit native-lib requirements when applicable, permissions/features and provenance. Test the independently extracted APK on a real emulator with original-game replay/input/lifecycle and retain visual PNGs.
5. **Device claims:** Keep phone-class GPU/memory/performance, thermal, orientation, process-death recovery, accessibility and physical-device compatibility as separate [release certification](release-certification.md) work. A single software emulator cannot certify all devices.
6. **External actions:** Play Console enrollment, private keys, app creation/listing, upload and publishing require the legitimate account owner and explicit authorization. No automatic credential creation, secret exfiltration, upload, staged rollout or claim of reviewer approval.

## Acceptance contract

P2 can close **preflight** only when source/build/runtime evidence and independently versioned Play policy/compliance checks are machine-readable, reproducible and fail closed on missing external attestations. If a Play Console owner action is outstanding, report `blocked-by-external-account` rather than `PASS`. A separate Play-published verdict requires independent Console evidence of review and release; no local certificate or manifest can self-issue that verdict.

Priorities: P2-0 static store-contract and policy freshness audit → P2-1 production-owned upload signer integration and external attestations → P2-2 Android extracted-release runtime and physical device sample validation → optional explicit Play Console submission workflow. Scope only what can be proven; do not add a new game engine, arbitrary JS→Godot converter, or iOS signing dependency here.
